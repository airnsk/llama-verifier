## Блок 0. Две обязательные проверки ПЕРЕД стартом V2 (новое, из разбора апстрима)

Эти два пункта появились из анализа текущего master llama.cpp — оба бьют по нашей архитектуре, оба проверяются замером, не по коду:

### 0.1. Совместимость с kv_unified
В master при авто-слотах по умолчанию включён kv_unified (единый KV-буфер на все последовательности). Известен свежий баг #25345: при kv_unified сервер МОЛЧА игнорирует штатную спекуляцию (-md) — без предупреждения. Наш путь собственный, но это сигнал, что зона шаткая.

Задача: прогнать существующий тест 16/16 (REPLAY FULL) в двух конфигурациях — с kv_unified и с -kvu (отключён). Если результаты различаются хоть в одном accepted — стоп, доклад, разбор. Зафиксировать в DECISIONS.md, какая конфигурация является референсной для V2+.

### 0.2. Границы отката GDN-состояния
Наша модель — гибрид с рекуррентным состоянием. Unified-кеш для рекуррентных состояний НЕ умеет произвольный откат: он ограничен bounded rollback (n_rs_seq), дальше — чекпоинты (-ctxcp/-cms); если точка возврата не покрыта — молчаливый n_past=0 и ПОЛНЫЙ ре-префилл (по логам видно как внезапный prefill_ms >> 0 на «тёплом» запросе).

Наш рабочий паттерн — частый частичный откат: принял j из K, откатил K−j (обычно 0–16 токенов), плюс ветки N цепочек.

Задачи:
1. Микрозамер: 1000 раундов verify с реальным распределением j (взять run-tails из этапа 0), мониторить prefill_ms каждого раунда. Критерий: prefill_ms ≈ 0 во ВСЕХ раундах после первого. Любой всплеск = ре-префилл = найти границу n_rs_seq экспериментально.
2. Замерить максимально безопасную глубину отката (бинарным поиском по K−j): где заканчивается bounded rollback для нашей модели/конфига.
3. Решить и зафиксировать: либо наш диапазон откатов всегда в пределах безопасной зоны (доказать), либо настроить чекпоинты под ритм раундов (чекпоинт каждые N принятых токенов), либо явный workaround (например, re-decode суффикса). Решение — с цифрами в DECISIONS.md.
4. Проверить --cache-reuse (по умолчанию выключен): наш паттерн «префикс растёт на j токенов за раунд» — прямой кандидат. Замерить экономию на тёплых раундах.

## Блок V3. temp>0 (после V2)

1. mode=exact: q[] в запросе, min(1, p/q), bonus из norm(max(0, p−q)). Валидация входа (q ровно K элементов → иначе 400).
2. mode=threshold с tau из конфига.
3. Статистический тест: ≥20k токенов через верификатор (temp=0.7) vs честный сэмпл таргета; χ²/KL на согласованном корпусе. Расхождение выше шума = баг, чинить до зелёного.
4. Напоминание из этапа 0: при temp 0.7 agreement НЕ хуже temp 0 (code 0.916/0.916) — ожидание: A(K) при 0.7 близко к жадному. Если замеры покажут систематически другое — доклад, это изменит рекомендации по дефолтному режиму.

## Блок V5. Стресс и финал

1. Регрессии: бит-эквивалентность N=1 (с оговоркой), 10k раундов без утечек KV-слотов (мониторинг свободной памяти кеша), граничные случаи (пустая цепочка, K=1, j=0, префикс > n_ctx → честная ошибка).
2. KV-стресс: кеш заполнен >90%, активное LRU-вытеснение — корректность ответов + предсказуемая деградация (тёплый клиент может стать холодным → ре-префилл — это ДОЛЖНО быть видно в метриках, а не молча).
3. Финальная матрица: {K ∈ 4,8} × {S ∈ 1,2,4} × {домен} — медианы 3 прогонов.
4. RESULTS.md финал: все таблицы, сравнение с прогнозом (ожидание sync ~30–35 t/s с драфтером 80 t/s; потолок верификатора ~55–60 t/s при K=8), глава «не замерено / известные ограничения» обязательна.
