## D-001 (06.09.2026) — Issue #27428 проверен, риска нет

(подтвердить на нашем железе, цифру issue на CMP 50HX не переносим).

## D-002 (06.09.2026) — Точка инъекции внешних цепочек в master
Аудит `tools/server/server-context.cpp` @73a43d1f:
- `slot.spec_draft` заполняется исключительно из `common_speculative_get_draft_params(...).result`
  (внутренние имплементации). HTTP-полей для передачи внешних draft-токенов нет.
- `handle_last_sampled_token()` (строка ~505): если `spec_draft` непуст — токены добавляются в
  батч подрядчиками после sampled-токена с инкрементом позиции; `spec_i_batch` хранит индексы
  выходов под каждую позицию. Дальше сличение с логитами таргета и `common_speculative_accept()`.
- Это ровно семантика «пакетная верификация одной цепочки». Для N цепочек нужен другой путь:
  одна итерация с ubatch из K токенов цепочки и выбором argmax по каждому выходу (см. V0-эскиз),
  либо N параллельных слотов (каждая цепочка = свой слот с одинаковым префиксом через prefix cache
  seq-share) — решение примем после кривой T(K,N), оба варианта задокументировать.

## D-004 (06.09.2026) — Реализация верификатора: отдельный бинарь на libllama vs патч llama-server
Аудит master 73a43d1f:
- llama-server: путь спекуляции жёстко завязан на внутренние имплементации
  (`common_speculative_get_draft_params(...).result = &slot.spec_draft`, GGML_ASSERT
  `slot.can_speculate()`), инъекции из HTTP нет. Переиспользование = патч server-context
  (трогать машину состояний слотов, ~риск регрессий).
- `llama_batch.logits` = `int8_t*` (output per token), `llama_get_logits_ith(i)` — row i из
  компактных output-ов: достаточно выставить logits=1 на позициях кандидатов.
- `llama_memory_seq_rm(seq,-1,-1)` / `seq_cp` — дешёвый откат хвоста KV, bonus-чек free.
Решение V1: **отдельный бинарь `verifier-test` на libllama** (src/verifier/, свой
мини-HTTP на vendored cpp-httplib, 1 слот = 1 сессия, префикс-кеш через seq-идентичность
без per-session KV: один seq, раунды последовательные). Обоснование:
1) нулевой риск сломать llama-server-регрессии; 2) полный контроль батча = фиксированная
форма ubatch → честный регрессионный тест бит-эквивалентности; 3) конвейеру всё равно,
какой бинарь отвечает за протокол; 4) патч llama-server остаётся запасным путём V2 (батчинг
слотов tam уже решён внутри сервера). V2-решение пересмотрим по данным V0: если одно-
секвенционный путь упрётся в GPU-idle между раундами — переход на fork llama-server с
инъекцией в spec_draft через HTTP.

## D-009 (06.09 15:11-15:19) Эксперимент 1 (dbg_batch): батч == последовательный эталон; причина acc=1 — сама цепочка self16 была испорчена конвейером rs-rollback
Эндпоинт /dbg_batch: A = батч K токенов на ветке seq 1; B = j-й батч [tok0..tokj] с
logits только на j (последовательный ground truth). Замер (префикс 504, K=16):
batch_rows == seq_rows по всем 16 позициям. Маски/состояния в батче НЕ сломаны.
НО: batch_rows[1]=2551 ≠ self16[1]=3572 — т.е. self16 (сгенерирована trunk-конвейером
np1/rs18, 16/16 раундов self-accepted) расходится со СВЕЖЕЙ greedy с позиции 2:
каждый раунд конвейера проверял себя от своего же (возможно испорченного откатом)
состояния — самоподтверждающийся дрейф, а не сверка с реальной моделью.
Прогон REFRESH-цепочки (построена итеративно из самих батч-строк): батч-верификация
приняла 11 из 12 токенов + bonus (обрыв self-confirm на шаге 11: причина не
установлена — fp-флип vs состояние; требует отдельного замера, не блокирует).
Итог: acc=1 при self16 — артефакт генерации цепочки, не верификатора. Для V0/V1
цепочки строить штатным drafter-путём или REFRESH-итерациями; trunk-rs-пайплайн для
этого не использовать.

## D-013 (06.09.2026 18:55) — V2: сессии на 2 seq (ствол+ветка), p0-на-ветке вместо отката
- Слот сессии = tr=2s+1, br=2s+2 (seq 0 — только stateless /vverify; режимы взаимоисключающие,
  проверка в round_verify). Очередь: пул httplib 16, single-worker склейка по окну --window (8 мс),
  promise/future на раунд; 429 при queue>64/занятой сессии/перерасходе ячеек (клетки:
  sum(prefix+chain)+16 <= n_ctx, учитываются собственные ячейки веток поверх shared ствола).
- **Ключевое: p0 досчитывается НА ВЕТКЕ** (seq_cp ствола [0,L-1) + decode tok[L-1]), ствол
  НЕ откатывается. Причина: путь V1 (частичный rm +1 токен на ствол) на сессиях дороже
  пересчёта — замер 18:40: rm на L-1 возвращает false, полный reset = 879–1531 мс на раунд.
  Повтор позиции на ДРУГОМ seq разрешён (strict X>max — внутри seq).
- Коммит ленивый как в V1 (accepted = дельта-pp следующего раунда, 1..K+1 токенов общим
  батчем по всем сессиям: разные seq в одном decode — маски не смешиваются, exp1/D-010).
  PM_RETR (ретракция ниже кэша) — полный reset (цена 0.2: ~0.9–1.5 с), PM_MISS-with-mismatch
  — последовательный trunk_extend.
- Раунды-тайминги: prefill_ms — доля на сессию (общая дельта/|items|), verify_ms — общий
  на батч; в отчётах V2 это единственные честные гранулярности.

- **Дополнение (хозяин, 06.09 19:18) — D-013 это инвариант, не просто оптимизация.** p0-на-ветке выбрано не только ради скорости: если ствол НИКОГДА не откатывается, а ветки одноразовые, то весь класс проблем GDN-отката (bounded rollback, чекпоинты, #25345-подобные сюрпризы recurrent-кеша) не касается сессийного пути. Цена — +1 токен декода на ветку. При миграции на другие версии libllama/железо это правило сохранять: никаких частичных rm/compress на стволе сессии.
