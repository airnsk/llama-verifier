# Промт для агента: верификатор спекулятивных цепочек как сервис на базе llama.cpp

## Контекст и мотивация (прочитать обязательно)

Мы строим асинхронный конвейер спекулятивного декодирования: внешний быстрый драфтер (MoE, на отдельной машине) поставляет цепочки токенов, а этот сервис — верификатор на большой плотной модели — проверяет их пакетно. Этап 0 (калибровка согласия моделей) завершён, результаты в `llm-launch-optimization/pipeline-moe-draft/PIPELINE_RESULTS.md`: min(A,B) argmax-agreement 0.759–0.938 по 8 ячейкам, эмпирические A(K) собраны, гейт BUILD пройден.

Текущая задача — **только верификатор**: отдельный сервис на базе llama.cpp, который обслуживает запросы вида «префикс + цепочки кандидатов» и возвращает, сколько токенов принято и какой токен следующий. Драфтер, транспорт и конвейер — НЕ часть этой задачи (будут отдельно); но API верификатора проектируется под них с самого начала.

Ключевые проектные решения, уже принятые и не подлежащие переобсуждению (если только не найдёшь фактическую ошибку — тогда остановись и доложи):

1. **Без состояния по протоколу.** Клиент присылает весь префикс текстом (или список token ids). Совпадение с уже посчитанным — за счёт prefix cache сервера (longest match). Никаких session id, никакой передачи KV по сети. Откат при отклонении цепочки — бесплатный: непринятые суффиксы просто вытесняются/не переиспользуются.
2. **Ответ — только конкретные токены.** Никаких распределений обратно клиенту не уходит.
3. **temp=0 — основной режим v1**, побочно точный (совпадение argmax). temp>0 — отдельный этап, два режима: точный (клиент присылает q[] — вероятности, с которыми драфтер выбрал каждый предложенный токен, K чисел на цепочку) и практичный (порог p > τ).
4. **Верификация — это маленький префилл.** Стоимость раунда ≈ стоимость прогона K×N токенов через таргет. Поэтому сервер обязан уметь собирать запросы от нескольких клиентов в один батч.
5. Целевая модель стенда: **Qwen3.8-27B-GSQ-RCO-IQ3_S.gguf** (указана хозяином 06.09 15:23; ранее в этой строке ошибочно был Q4_K_XL — замеры 06.09 до 15:22 на Q4_K_XL, повторить на GSQ-RCO), KV-кеш НЕ квантовать, размещение — 2 GPU (P40-класс, layer split; проверить issue #27428 — MTP на 2-GPU split уполовинивает PP, нам MTP не нужен, но слой-сплит проверить на всякий случай).

## Спецификация протокола (реализовать как HTTP API поверх/рядом с llama-server)

### Запрос

```json
{
  "prefix_tokens": [ ... ],            // весь префикс; сервер сам найдёт longest match с кешем
  "chains": [
    {
      "tokens": [t1, t2, ..., tK],     // одна цепочка кандидатов
      "q": [0.61, 0.30, ...]           // ОПЦИОНАЛЬНО: вероятности драфтера, только для точного temp>0
    }
  ],
  "mode": "greedy" | "exact" | "threshold",
  "tau": 0.3,                           // только для mode=threshold
  "temperature": 0.0,
  "client_hint": "code"                 // ОПЦИОНАЛЬНО: доменная подсказка для адаптивного K (этап 4)
}
```

### Ответ

```json
{
  "chain_id": 0,                        // какая цепочка принята (фиксированный порядок проверки: 0,1,2...)
  "accepted": 5,                        // j — сколько токенов цепочки принято (0..K)
  "bonus_token": 12345,                 // следующий токен от таргета (всегда, даже при accepted=0)
  "tokens_out": [t1..t5, 12345],        // accepted префикс цепочки + bonus — готовый суффикс генерации
  "verify_ms": 41.2                     // честный тайминг раунда (для калибровки)
}
```

Семантика: приняты j первых токенов цепочки chain_id; tokens_out клиент дописывает к своему префиксу; остальные цепочки игнорируются. При j=0 всё равно возвращается bonus_token — раунд никогда не бывает пустым.

### Правила приёма

- **greedy (v1, дефолт):** токен цепочки принимается ⟺ он равен argmax логитов таргета на этой позиции. Первый mismatch → обрыв, bonus = argmax таргета на позиции обрыва.
- **exact (temp>0):** классический rejection sampling: принять токен t с вероятностью min(1, p(t)/q(t)); при отклонении bonus сэмплируется из нормированного max(0, p − q). Распределение выхода обязано совпадать с честным сэмплированием таргета — это проверяется тестом (см. этап 5).
- **threshold (temp>0, практичный):** принять, если p(t) > τ. Bonus — обычный сэмпл из p. Пометить в документации как НЕ сохраняющий распределение точно.

### Фиксированный порядок и детерминизм

Цепочки проверяются строго в порядке массива, принимается первая по порядку, давшая j > 0 (при равенстве — ранняя). Режим с одной цепочкой (chains.len == 1) обязан давать результат, бит-в-бит совпадающий с обычной greedy-генерацией тем же llama.cpp при том же сиде сборки — регрессионный тест обязателен. Учесть: llama.cpp НЕ batch-invariant — «бит-в-бит» проверять при фиксированной форме батча (убатч = одна цепочка), либо ослабить критерий до «совпадение при повторном прогоне той же конфигурации» и зафиксировать это в README честно.

## Этапы работы

### Этап V0. Воспроизводимость и базовая кривая стоимости

1. Зафиксировать окружение стенда (версия llama.cpp/коммит, модель, квант, флаги запуска, размеры ubatch/batch, n_ctx, GPU-сплит).
2. Снять кривую стоимости верификации: T(K × N) для K ∈ {2,4,8,12,16}, N ∈ {1,2,4} цепочек — именно на этом железе, через llama-batched-bench или собственный харнесс. Это таблица-фундамент всего сервиса: она определит, сколько цепочек и какой длины можно проверять за раунд.
3. Калибровочные A(K) взять из PIPELINE_RESULTS.md этапа 0 (не перемерять).

Критерий выхода: таблица T(K,N) + подтверждение, что T(K=8, N=1) существенно меньше 8 × T(TG-шаг).

### Этап V1. Односессионный верификатор (greedy)

1. Реализовать endpoint по спецификации выше (только mode=greedy). Вариант реализации на выбор: расширение llama-server, отдельный бинарь на libllama, или обёртка над существующим --spec-type механизмом, если его удаётся переиспользовать для внешних цепочек — решить по ходу, выбор обосновать.
2. Prefix cache: включить и ПРОВЕРИТЬ longest-match поведение (повторный запрос с префиксом, отличающимся только суффиксом, не должен пересчитывать общую часть). Замерить hit-экономию на повторных раундах.
3. Кеш-политика: accepted-суффикс остаётся в кеше (это будущий префикс следующего раунда), отклонённые суффиксы НЕ должны засорять кеш — проверить, что seq_rm/вытеснение работают как ожидается, утечек слотов нет.
4. Юнит-тест: скармливаем верификатору цепочки, снятые с реального драфтера (дампы из этапа 0), сверяем принятые длины с оффлайн-расчётом по тем же логитам. Совпадение 100%.

Критерий выхода: раунд verify по API на K=8, N=1 укладывается в T из таблицы V0 + ≤15% на оверхед; тест на бит-эквивалентность одиночной цепочки зелёный.

### Этап V2. Очередь и мультисессионный батчинг

1. Сервер принимает запросы от нескольких клиентов асинхронно, накапливает очередь с маленьким окном ожидания (параметр, дефолт ~5–10 мс) и склеивает запросы в один батч верификации.
2. ВАЖНО (вывод из нашего анализа): на этом железе батчинг сессий имеет насыщение — снять кривую throughput(число сессий) для сессий = 1..8 и найти точку, после которой per-session скорость падает неприемлемо. Результат — рекомендуемый лимит параллельных сессий в конфиге.
3. Справедливость: при переполнении очереди — честный отказ (HTTP 429 с Retry-After), не молчаливая деградация.

Критерий выхода: таблица «сессии × t/s на сессию × суммарный t/s», документированный лимит.

### Этап V3. temp>0: exact и threshold

1. mode=exact: принять q[] в запросе, реализовать min(1, p/q) + bonus из norm(max(0, p−q)). Валидация: q обязан иметь ровно K элементов, иначе 400.
2. mode=threshold с параметром tau.
3. Статистический тест точности exact-режима: сгенерировать ≥20k токенов через верификатор (temp=0.7) и честным сэмплированием таргета без спекуляции; сравнить эмпирические распределения (χ² или KL на согласованном корпусе промптов). Отклонение выше статистического шума = баг, искать до победного.

Критерий выхода: тест распределения зелёный; в README таблица «режим × эмпирический A(K) × t/s» (A(K) при temp 0.7 взять из этапа 0: code 6.07, prose 3.75).

### Этап V4. Адаптивный K и доменные профили

1. По client_hint (или авто-эвристике по эмпирическому acceptance последних раундов сессии — окно ~20 раундов) выбирать K из {2,4,8} под домен: code/reasoning/refactor → 8, prose-класс → 2–4.
2. Эвристика должна уметь понижать K динамически, если acceptance сессии упал (аналог p_mins из discussion #10466, но проще: порог по среднему j).
3. Все пороги — в конфиге, не в коде.

### Этап V5. Итоговые тесты и RESULTS.md

1. Регрессия: chains.len==1 бит-эквивалентность (с оговоркой про batch-invariance), отсутствие утечек KV-слотов на 10k раундов, корректность при граничных случаях (пустая цепочка, K=1, j=0, префикс длиннее n_ctx — честная ошибка).
2. Стресс KV: n_ctx заполнен >90%, prefix cache под вытеснением — сервер не падает, ответы корректны.
3. Финальная матрица производительности: {K} × {сессии} × {домен из этапа 0} — медианы 3 прогонов, готовность ≤40% расхождения между прогонами (иначе искать источник джиттера).
4. RESULTS.md: конфиг стенда, все таблицы, честная глава «что не работает/не замерено», сравнение с прогнозом из PIPELINE_RESULTS.md (ожидание: K=8, N=1, code → раунд ~41 мс, эквивалент ~140–150 t/s при высоком branch-hit; если получилось сильно хуже — разобраться и написать почему, это тоже результат).

- Медианы минимум 3 прогонов на всех скоростных замерах; в отчёте указывать разброс.
- Негативный результат — результат. Если мультисессионный батчинг не масштабируется — зафиксировать цифру и лимит, не подгонять.
- Никаких правок чисел «для красоты»; каждая таблица воспроизводима командой из README.
- Коммиты атомарные, сообщения на английском; RESULTS.md и README — на русском.
- При расхождении с этим промтом по архитектурному вопросу (например, переиспользовать --spec-type vs отдельный endpoint) — сначала замер/прототип, потом решение, и решение фиксируется в RESULTS.md с обоснованием.
- Из прошлых кампаний: остерегаться batch-shape fp-недетерминизма при интерпретации «расхождений»; CMP 50HX разблокирован, T1-кривая известна (29.3→28.8 мс/строка при B≤8) — если верификатор будем гонять и на ней, брать новые числа, не старые.
